# 犇犇的车库：对战模块开发计划

> 最新规则 v2：玩家氮气无限次、每次 2.5 秒、结束后恢复 1.25 秒；AI 每场两次不变。采用八类车身与按名称区分的性能，赛中显示座驾名称。本文旧版条目与此冲突时以本段和 [车型与氮气更新](车型与氮气更新.md) 为准。旧版未完成比赛按原快照继续。

- 日期：2026-10-22
- 状态：已完成首版开发；实现范围、验证结果与待校对项见 [对战模块验收记录](对战模块验收记录.md)。
- 本次更新（2026-10-23）：参考 FH3: Hot Wheels 的三个海岛场景制作橙色高架赛道；保持全自动驾驶，玩家仅控制氮气时机。
- 最新视觉要求：提高场景与动作细节；采用赛车正后方追身镜头，包括回环内随车翻转；目标为对齐参考游戏的赛道和场景布局。目前已实现材质、地形、阴影、特效与追身镜头升级；精确布局复刻待具体赛事或完整跑圈参考确认，详见场景参考文档。
- 已确定方向：赛前选车、赛中自动竞速与手动氮气，首版为一名玩家对两名 AI 的三车比赛，后续扩展真人联机

## 1．项目现状与设计目标

已检查当前项目：

| 当前基础 | 对战模块如何利用 |
|---|---|
| 694 张车辆卡，含名称、图片、系列和稀有度 | 复用车辆收藏与展示素材 |
| 首页、抽卡、车库图鉴 | 增加对战入口，打通选车流程 |
| 每日 10 次抽卡，已收集车辆不重复抽取 | 保持现有收藏机制 |
| 浏览器本地存档及 JSON 导入导出 | 扩展战绩、选车及未完成比赛存档 |
| 原生 HTML、CSS、JavaScript | 沿用现有页面结构，新增浏览器 3D 渲染层 |

目前车辆没有速度、操控等竞技属性，也没有比赛引擎，需要新增这些基础。

核心目标：**让收集到的车辆有上场价值，让赛前选车和氮气释放时机影响胜负，让玩家能看懂为什么赢、为什么输。**

## 2．首版功能范围

| 功能 | 首版安排 |
|---|---|
| 人机快速对战 | 一名玩家与两名 AI，三车同时竞赛 |
| 三种赛道 | 直线竞速道、岔路碰撞道、回环竞技道 |
| 自动驾驶 | 自动起步、加速、转向、路线选择、碰撞响应和冲线 |
| 玩家赛中操作 | 仅控制氮气释放时机，无驾驶策略选择、手动转向、刹车或漂移 |
| 车辆性能与定位 | 五项属性、五种定位，包含重量和冲撞型 |
| 3D 比赛场景 | 立体赛道、车辆模型、摄像机、碰撞及氮气效果 |
| 本地战绩及继续比赛 | 包含 |
| AI 难度 | 首版采用统一规则的 AI，暂不增加难度选择 |

首版对战每天可以玩 **5 次**，与每日抽卡次数独立。单场目标时长 **1 分钟以内**。

次数规则拟定为：完成资源加载、正式发车时扣除一次；刷新恢复同一场不重复扣除；赛前取消不扣除；发车后主动弃赛不退次数。每日按本地日期重置，与现有抽卡日期口径一致。跨日恢复旧比赛不扣新一天次数。本地次数属于单机规则，不作为未来在线竞技的可信凭证。

## 3．一场比赛的完整流程

1. 从首页或导航进入“对战中心”，查看今日剩余对战次数。
2. 选择赛道，查看赛道特点、两名 AI 对手及公开性能。
3. 从已收藏车辆中选一辆参赛。
4. 加载 3D 赛道与车辆，展示规则和氮气使用说明。
5. 倒计时后，三辆车自动发车并持续竞速，不在赛段之间暂停等待策略选择。
6. 玩家观察实时车速、位置、前方道路和剩余氮气，仅决定何时释放氮气；不操作时车辆也会自动完成比赛。
7. 冲线后结算名次、总用时、差距、氮气使用和碰撞等关键事件。
8. 次数足够时可以再次挑战、换车或更换赛道；次数用完后仍可查看战绩。

无车辆的新玩家可以使用固定的“体验车”。体验车不计入收藏，并在选车和结算时明确标记；体验车比赛也计入每日 5 次限制。

## 4．车辆性能与平衡方案

新增五项 **游戏内性能**，明确说明其不代表真实车辆测试数据。

| 属性 | 作用 | 主要受益场景 |
|---|---|---|
| 极速 | 改善高速路段成绩 | 长直道 |
| 加速 | 改善起步和出弯表现 | 起步、短冲刺 |
| 操控 | 改善弯道表现 | 连续弯道 |
| 稳定 | 降低碰撞、落地或复杂路段中的失稳损失 | 技术路段、碰撞与回环出口 |
| 重量 | 增加碰撞中的抗推挤与挤开其他车辆的能力 | 岔路交汇、碰撞赛 |

车辆先归入五种定位：极速型、加速型、操控型、均衡型、冲撞型。

数值设计原则：

- 各定位使用接近的属性总预算，通过长短板区分车辆。
- 稀有度继续体现收藏价值，不直接赋予全面碾压的性能。
- 普通车在适合的赛道和氮气时机下，可以击败传说车。
- 同车型不同批次或涂装原则上保持相同基础性能。
- 首版不设置永久属性升级，先验证基础竞速是否好玩。
- 重量不作为无代价加成：拟通过加速响应和碰撞恢复建立取舍，具体系数在原型阶段验证。

694 张卡的性能配置采用“定位模板＋车型映射”。不能仅凭车辆名称关键词推断全部性能；无法可靠识别的车型进入待校对清单，暂用均衡模板。

先挑选约 24 辆有代表性的车进行平衡验证，再覆盖完整卡池。

## 5．赛道与氮气规则

三类赛道分别采用 Thrill City（滨海天际线）、Jurassic Jungle（恐龙丛林）、Hyperloop（海上巨环）作为场景参考，沿用下表的玩法类型。采用程序化 3D 几何重建主题元素，路线按一分钟内比赛重新设计。场景来源与改编边界见 [场景参考](../assets/battle/场景参考.md)。

| 赛道 | 场景设计方向 | 玩法重点 |
|---|---|---|
| 直线竞速道 | 起步区、加速直道、终点冲刺区 | 加速、极速与氮气时机 |
| 岔路碰撞道 | 分岔与汇合路段，允许车辆接触和推挤 | 自动路线选择、重量、稳定与碰撞前后氮气时机 |
| 回环竞技道 | 立体回环与衔接直道 | 自动贴合赛道行驶、速度保持、稳定与回环前后氮气时机 |

路线选择由自动驾驶决定，玩家不选择岔路。回环的具体形状、护栏和碰撞恢复方式在场景原型阶段细化。建议首版采用受约束的街机运动模型，保证所有车辆在不使用氮气时也能完成回环，不因低速永久卡在场景中。

氮气规则：

- 保留每场初始 **2 次**，改为实时按钮触发，不再采用“单段最多一次”的回合规则。
- 有效触发时消耗 1 次并立即进入加速状态；持续时间和增益作为待调参数。
- 生效期间不可重复叠加；结束后可再次释放。按键长按不连续消耗次数。
- HUD 明确显示剩余次数、正在生效状态及禁用原因。
- 不提供赛中恢复；玩家可选择整场不使用氮气。
- 增益随车辆状态和路段变化，在碰撞区或回环附近的效果必须有清晰反馈。
- 玩家和 AI 使用相同次数、增益和触发限制。

随机因素只用于有限、可复现的行为差异，不加入随机爆胎或随机淘汰。碰撞影响来自车辆状态和碰撞规则，不能用无依据的随机处罚替代。

## 6．比赛模拟、自动驾驶与 AI

采用连续时间的比赛模拟，取消旧的“赛段用时减去策略收益”公式与分段提交机制。赛道可分区用于参数配置、事件记录和结算分析，但比赛过程持续进行。

每个固定模拟步更新：

1. 根据车辆属性、当前速度、路段曲率及氮气状态计算驱动与速度上限。
2. 自动驾驶计算目标路线、转向和必要减速；玩家车辆同样自动驾驶。
3. 更新三车位置、赛道进度、碰撞与稳定状态。
4. 检测冲线、排名、比赛超时等事件，记录模拟时间。

具体要求：

- 三辆车共用同一运动与碰撞规则，不给予 AI 隐藏速度或重量优势。
- 两名 AI 依据公开赛况决定氮气时机，不预知玩家未来输入。
- 使用固定模拟步长，3D 渲染插值展示，避免显卡帧率直接影响车速和成绩。
- 氮气输入记录为模拟步编号；同规则版本、配置、种子和输入序列应能复现结果。具体复现精度在原型阶段验证。
- 内部使用统一模拟时钟，显示精度与判名次规则一致。冲线时间相同则并列。
- 结算记录第 1、2、3 名或并列；胜场定义为获得第 1 名，弃赛单独统计。
- 碰撞不能导致穿出赛道、无限抖动或永久卡死；恢复规则和损失上限在原型阶段确定。
- 建议设置 60 秒比赛上限：未冲线车辆标记未完成，并在已冲线车辆之后按有效进度排名；此细节在规则定稿时确认。
- 切换后台时暂停本地比赛并保存，返回后提示继续，避免玩家失去氮气操作机会。

## 7．页面与 3D 视觉设计

延续现有的深色车库、红橙火焰、黄色强调色和稀有度配色。比赛主体必须是实时 3D 场景，不使用车辆卡片或二维进度条替代比赛场景。

| 页面或区域 | 主要内容 |
|---|---|
| 首页 | “进入对战”按钮、近期战绩摘要 |
| 对战中心 | 赛道、今日剩余次数、规则说明、继续比赛 |
| 选车区 | 已拥有车辆、五项性能、定位、赛道适配 |
| 比赛区 | 3D 赛道和三车、自动跟随镜头、名次、车速、时间、差距、氮气按钮 |
| 结算区 | 三车名次、用时、关键氮气与碰撞事件、再次挑战 |
| 车库详情 | 性能面板、“使用此车对战”入口 |

3D 场景计划：

- 统一采用晴日蓝天、碧海群岛、橙色塑料轨道、蓝色高架支撑；三条赛道分别突出玻璃高楼、机械恐龙与巨型垂直回环。
- 海面波光和恐龙下颌为可关闭的环境动画；恐龙不参与碰撞判定。环境代码独立置于 `js/battle-environment.js`。

- 建立赛道几何、路面、护栏、场景灯光和自动跟随摄像机，确保关键路段可观察。
- 展示真实三维车辆模型、轮胎转动、氮气尾焰及适量碰撞反馈。
- 当前车辆照片保留用于选车与图鉴，不能直接充当 3D 车型资产。
- 首版建议用少量风格统一的低多边形车身模板，按车辆映射并用颜色、编号等区分；不承诺为 694 张卡分别制作精确模型。该资产方案待细化。
- 三车身份标识清晰，玩家车辆始终易于识别；镜头不因碰撞剧烈晃动。
- 提供画质档位和减少震动、粒子效果选项，保留 3D 主体。
- 场景加载失败或设备不支持渲染时给出明确提示，并在正式发车前阻止扣次。

交互要求：

- 首版优先电脑端，鼠标点击氮气按钮；可用空格键触发同一动作，并防止按键重复触发。
- 比赛中的竞技输入只有氮气；不出现策略、路线、加速、刹车或转向控制。
- 比赛中不提供跳过至结果功能，以免跳过可操作的氮气时机；可跳过不影响玩法的赛前、赛后演出。
- 名次、剩余氮气与差距同时用文字和数值表达，不只依靠颜色。
- 在原型阶段确定基准电脑、分辨率和性能预算，再验收三车与碰撞同时出现时的流畅度；手机适配作为后续评估项。

## 8．存档、奖励与异常处理

建议在现有存档中加入带版本号的 `battle` 数据区，保留收藏、每日次数和抽卡轮次。

保存内容包括：

- 默认选车；
- 总场次、各名次次数、并列记录和弃赛次数；
- 每日对战日期、已使用次数和已扣次比赛标识；
- 各赛道最佳成绩，并标注规则版本；
- 最近 30 场记录；
- 当前比赛的三车状态快照、模拟步、种子、氮气输入记录、剩余氮气及进度；
- 已完成结算的比赛标识。

首版奖励建议采用赛道徽章、首胜记录和个人最佳，不发放额外抽卡次数，避免同时引入新的经济平衡问题。

异常处理计划：

| 情况 | 处理方式 |
|---|---|
| 刷新或关闭页面 | 从最近已保存的比赛节点继续 |
| 连续点击或长按氮气按钮 | 生效期间拒绝重复触发，扣减次数与状态更新保持一致 |
| 重复打开结算页 | 同一比赛只记录一次战绩 |
| 主动退出已开始的比赛 | 明示后记为弃赛，不退对战次数；赛前退出不计战绩且不扣次 |
| 导入旧存档 | 保留原有进度，补齐对战默认值 |
| 导入损坏存档 | 校验失败时拒绝覆盖当前存档 |
| 多标签页同时对战 | 只允许一个标签页推进同一场比赛，其他页面提示刷新或接管 |
| 本地存储不可用 | 允许当前会话临时体验并执行会话内次数限制；明确提示无法持久保存战绩和每日次数 |
| 3D 渲染中断 | 暂停模拟并保留快照，恢复后继续同一场，不重复扣次 |

继续沿用相同本地访问地址，避免因域名或端口变化导致浏览器读取不到原有收藏存档。

## 9．技术拆分与实施顺序

模块划分如下；首版已按此结构实现。

| 计划文件 | 职责 |
|---|---|
| `battle.html` | 对战页面结构 |
| `css/battle.css` | 对战布局、响应式和动效 |
| `js/battle-data.js` | 车辆性能、赛道、规则配置 |
| `js/battle-engine.js` | 固定步长运动、碰撞、冲线、种子与输入记录 |
| `js/battle-scene.js` | 3D 渲染、摄像机、模型加载和视觉效果 |
| `js/battle-tracks.js` | 三类赛道几何、路线与碰撞区域 |
| `assets/battle/` | 3D 模型、纹理等资源，记录来源与使用许可 |
| `js/battle-ai.js` | 三车自动驾驶与两名 AI 的氮气决策 |
| `js/battle-store.js` | 比赛恢复、每日次数、战绩及结算去重 |
| `js/battle.js` | 页面交互与演出协调 |

现有存储模块需要补充受控更新接口、版本迁移及导入校验，避免多个模块各自覆盖整个存档。车辆原始数据文件标记为自动生成，因此竞技属性独立存放，按车辆 ID 关联。

3D 渲染层拟使用浏览器 WebGL 引擎，具体库及版本在实施前确认。物理采用适合街机竞速的受约束运动与碰撞模型，优先验证回环、岔路汇合和重量影响；逻辑层与渲染层分离，避免界面动画决定比赛结果。

实施阶段建议如下：

| 阶段 | 工作内容 | 完成标准 |
|---|---|---|
| 1．规则定稿 | 三车、每日 5 次、氮气、碰撞、回环、排名及超时 | 规则完整，消除分段策略与实时竞赛冲突 |
| 2．3D 技术原型 | 一条样例赛道、三车自动行驶、镜头、氮气、碰撞及回环验证 | 能观察并操作氮气，确认可实现性与性能基线 |
| 3．数值与比赛引擎 | 24 辆代表车、五属性、固定步长、自动驾驶、输入记录 | 可复现比赛，无明显万能定位；不放氮气也能完赛 |
| 4．三条赛道与流程 | 直线、岔路碰撞、回环；选车到结算 | 三车在各场景完整完成比赛，目标时长在 1 分钟以内 |
| 5．项目集成 | 首页、车库入口、每日次数、恢复、导入导出 | 原有收藏及抽卡正常，对战次数只扣一次 |
| 6．完整卡池 | 全部车辆属性与 3D 模板映射 | 每辆车均有合法配置及可用模型，无缺失导致的阻断 |
| 7．体验验收 | 电脑操作、3D 性能、异常恢复、平衡调整 | 达到下述验收标准 |

## 10．验收标准与后续扩展

首版必须通过的检查：

- [ ] 新玩家使用体验车、老玩家使用收藏车，均能完成比赛。
- [ ] 一名玩家与两名 AI 同场，直线竞速、岔路碰撞、回环竞技三类 3D 赛道全部可玩。
- [ ] 车辆全自动起步、行驶、选路、转向和冲线；玩家赛中只能控制氮气时机。
- [ ] 不操作氮气也能正常竞赛；取消所有赛段策略选择和等待提交界面。
- [ ] 每场 2 次氮气，重复点击或长按不会重复消耗；AI 遵守相同限制。
- [ ] 每天最多正式发车 5 次，与抽卡次数独立；恢复同一场不重复扣次。
- [ ] 比赛目标时长在 1 分钟以内，超时、并列、弃赛都有明确定义和结果。
- [ ] 五项属性、赛道适配、重量碰撞与氮气时机对成绩有可解释的影响。
- [ ] 3D 场景包含立体赛道、三车模型、跟随镜头和氮气反馈，不用二维动画替代。
- [ ] 回环与碰撞不会导致永久卡死或无法结算。
- [ ] AI 无隐藏属性优势，不预知玩家未来氮气输入。
- [ ] 相同版本、配置、种子和输入序列可复现结果，帧率不直接改变比赛速度。
- [ ] 刷新、重复点击、重复结算不会重复增加战绩或消耗次数。
- [ ] 旧存档导入后收藏和抽卡次数保持正确；对战不会解锁未拥有车辆。
- [ ] 资源缺失、存储失败、渲染中断等情况有明确提示和恢复或退出路径。
- [ ] 电脑端可以完成选车、氮气操作和结算，达到原型阶段确定的 3D 性能基线。

平衡验证采用批量模拟，对比五类车辆、三类赛道和不同氮气时机；检查是否存在通吃赛道的车型、无代价的重量优势、必胜氮气时点，以及 AI 是否通过隐藏数值获胜。

后续真人联机需要增加身份、房间、服务端存档和服务端权威结算。当前本地收藏与成绩可被用户修改，不能直接作为在线排位依据。首版会保留清晰的比赛输入、行动记录和规则版本接口，为联机复用计算逻辑做准备。
